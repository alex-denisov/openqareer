## Цель

Движок держит весь пул в памяти и читает базу только на старте (`restore`).
Нужно, чтобы каталог, админка, подбор и сведение кластеров работали из SQLite,
а в куче жили только данные текущего запроса. Тогда 450 000 записей hh.ru (или
2 млн) отличаются от 134 000 только диском.

## Срезы (каждый уменьшает память и выкатывается отдельно)

0. **Замер (первым, без него остальное — догадка).** После выката B220 читать
   `/api/v1/health` → `memory` на проде: байт кучи на запись. Профилем кучи (на
   копии базы локально, не на проде) назвать, кто держит память: сырые записи,
   кластеры, индексы подбора, снимки `matchedPoolSnapshot`.
1. **Каталог и админка из SQL:** страничный вывод, счётчики по источникам, FTS5
   по названию/компании; `getVacancies` перестаёт копировать весь пул.
2. **Подбор:** SQL-префильтр (роль, регион, свежесть, текст) до сотен кандидатов,
   скоринг в памяти только по ним.
3. **Кластеры в таблице, инкрементально:** при слиянии среза источника
   пересчитываются только затронутые кластеры, глобальной пересборки нет
   (сейчас 2,8 с на 42К после фикса квадратичности, на 500К — минуты).
4. `restore` больше не поднимает всё в память; `rawVacancies` уходит.

## Границы

- Не менять контракт частичного/полного чтения (B214/B219): `replaceSourceSlice`
  / слияние остаются, но выполняются в SQL.
- Честность счётчиков (B161/B192): «в пуле» считается по базе, а не по памяти.

## Срез 1 — пул читается из хранилища, `rawVacancies` снят (2026-09-15)

Срезы 1 и 4 плана сделаны одним выкатом: без снятия `Map` из движка память
не уменьшилась бы вовсе, а «админка из SQL» при живой копии в куче — только
подготовка.

**Что изменилось.**
- `VacancyPoolStore` отвечает на вопросы движка сам: точечное чтение, счётчики
  (всего, по площадкам, срез площадки с долей активных), страничная выдача с
  фильтрами, ссылки площадки для обхода живости, слияние частичного чтения и
  снятие по `dropObservedBefore` (B219) — всё в SQL.
- Движок не держит ни одной записи: в куче живут только кластеры. Сведение
  читает свежий срез из базы на время сборки (полная пересборка — до среза 3).
- Узкая таблица `vacancy_pool_index` рядом с `vacancy_pool`. Колонка, добавленная
  после `payload`, лежит в строке за ним, и фильтр по ней читает всю таблицу с
  текстами: 7 с на запрос при 100 000 записей (замер). Узкая строка — десятки
  миллисекунд; `payload` берётся точечно только для страницы.
- Записи, сделанные до B221, получают строку индекса фоновым проходом порциями
  по 2 000 в `restoreAsync` (30 с после `listen`, как и прежний `restore`).
- Для тестов без базы — `MemoryVacancyPoolStore`; тест паритета гоняет обе
  реализации по одному набору вопросов.
- Обход живости берёт `{id, url}` вместо записей целиком.

**Замер (локально, синтетический пул 100 000 записей ≈ 7 КБ JSON, 100 000
кластеров, одна база для обоих замеров).**

| Показатель | До (`fb70ff6`) | После |
|---|---|---|
| Куча после `restore` + сведения | **639 МБ** | **200 МБ** (−69 %) |
| `restore` + сведение | 5,8 с | 6,3 с |
| Страница админки без фильтра | — | 37 мс |
| Счётчики по площадкам | — | 11 мс |
| Текстовый поиск админки | 0,3 с | 1,0 с |
| 10 000 точечных проверок (`isKnown` hh) | — | 215 мс |
| Ссылки площадки для обхода | — | 0,3 с |

Оставшиеся 200 МБ — кластеры (~2 КБ на кластер): срез 3.

**Отклонения от плана.**
- Поиск админки — `instr` по заранее опущенной в регистр строке, а не FTS5:
  прежняя семантика (подстрока, любой алфавит) сохраняется точно; FTS5 ставит
  словесный, а не подстрочный поиск. Линейно: ~1 с на 100 000, ~5 с на 450 000.
  Маршрут только для админа; если станет мешать — FTS5 отдельным срезом.
- Похороненное объявление, которое площадка показала снова, остаётся
  похороненным и в выдаче (раньше `Map` его показывала, а база — нет).

**Первый старт после выката (100 000 записей без индекса).** Дочитывание
8,7 с в фоне порциями по 2 000 с курсором по `rowid`; максимальная пауза
цикла событий 343 мс; асинхронное сведение читает записи из базы по одной
(6 с, те же паузы). `/health` отвечает всё время.

**Ревью (code-reviewer, security-reviewer) — закрыто в этом срезе:**
- Сведение при старте читало весь срез синхронно — заменено на курсор базы с
  уступкой цикла событий по мере сборки.
- Замена среза шла через индекс и не видела строк, ещё не дошедших до него;
  теперь по собственным колонкам пула, а признак похороненности первичная
  строка индекса берёт у пула.
- Дочитывание: ключ индекса — ключ строки, не поле из текста (иначе проход не
  кончался бы); курсор по `rowid` вместо квадратного перебора; тихого
  удаления при любой ошибке нет — удаляется только нечитаемая строка, прочее
  всплывает в лог старта.
- `isKnown` быстрого прохода hh — по индексу, без чтения текста.
- Пул в памяти ключует срез по площадке-аргументу, как `source_id` в базе;
  паритет расширен на `prune`, `markExpired`, итератор и этот случай.
- Безопасность: WARN → закрыто. Игла поиска ограничена 80 знаками
  (`adminVacancyQuerySchema`), маршрут списка — 60 запросов в минуту; все
  значения — связанные параметры (проверено враждебным вводом).
  Открытое: поиск линейный по описаниям — FTS5 или срез `search_text`
  отдельным тикетом, если станет мешать.

## Выкат 1 (2026-09-15 21:24 MSK, `b8a3d2e`) — откачен в 21:38

Сразу после старта: куча **82 МБ** (было 1 113), дочитывание индекса 173К
строк прошло в фоне за ~3 мин. Но каждая волна опроса (раз в 5 минут)
вызывала синхронное `recluster()`, а оно читает и разбирает все 173 635
записей из базы: на VM прода это **1–2 минуты процессора** (локально — 4 с),
и `/health` не отвечал по 90+ с. Откат `openqareer-rollback` → `fb70ff6`.
Старый код блокирует так же, но только на старте (`loadVacancies` внутри
`restoreAsync` разбирает всё синхронно) — отсюда и «окно здоровья 20 с».

Урок: цена одного полного чтения пула на проде — минуты, не секунды; любая
полная пересборка из базы на каждую волну невозможна до среза 3.

**Исправление вперёд:** режим сведения `background` (только прод):
асинхронно, уступая цикл событий, не чаще раза в 15 минут, одна сборка за
раз; чтение отдаёт текущие кластеры и никогда не ждёт. Тесты — прежний
`sync`. Синхронный `recluster()` тоже читает потоком, а не массивом.

## Выкат 2 (21:56 MSK, `fabc96e`, фоновое сведение) — откачен в 22:18

За 20 минут: куча пилой **36 → 1 407 МБ** (предел 1 632), `/health` до 30 с
и 502. Асинхронное сведение уступает цикл, но каждый проход разбирает
1,2 ГБ JSON — записи переживают молодое поколение и копятся в старом до
предела кучи, где сборщик мусора на медленном CPU останавливает процесс
на десятки секунд. Откат → `fb70ff6`; на `main` три коммита B221
отменены `git revert` (`4644e7c`), работа сохранена в ветке
`b221-pool-out-of-heap`.

**Вывод.** Замена «пул в куче» на «читать пул из базы целиком при каждом
сведении» на этой VM не работает: мусора столько же, сколько раньше было
живых данных. Дальше только без полных проходов:
1. Компактная проекция для сведения (название, работодатель, ссылка,
   отпечаток, навыки, 300 знаков описания, источник) в отдельной колонке
   индекса — 10–15× меньше разбора и мусора за проход; и/или
2. Срез 3 — инкрементальные кластеры в таблице: волна пересчитывает только
   затронутые, полного прохода нет.
Обе меры нельзя проверить локально (локально проход — 4 с) — нужен
согласованный с владельцем выкат-эксперимент в тихое время с откатом
наготове.

## Production correction — 2026-09-19

После роста production базы до примерно 559 405 вакансий и 380 717 кластеров
выяснилось, что bounded public `LIMIT 24` не был достаточен: `restore`,
`healthOf` и первый `syncDue` всё ещё могли вызвать полный `loadClusters()`.
Это приводило к OOM или D-state блокировкам event loop на origin.

Исправление продолжено в [B229](./B229-production-safe-lazy-vacancy-catalog-and-maintenance.md).
В B221 зафиксированы следующие закрытые runtime-обходы:

- SQL page read для кластеров и индекс `(updated_at DESC, id ASC)`;
- SQLite restore без полной гидрации cluster snapshot;
- source health без полной гидрации;
- bounded startup pruning через индексы;
- production startup в read-only lazy mode без replay/recluster/source-sync на
  основном HTTP event loop.

Финальный production SHA: `9bb256c73472ddcf05b8c045354fa06f421be9c7`.
CI `35461714371` прошёл Verify и Deploy. Origin, `eterapy-3` и `eterapy-4`
подтвердили HTTP 200 для `/health` и `/vacancies` после warm-up.

Срез не закрывает B221 целиком: полноценная `catalog_entries` projection,
keyset pagination для page 2+, SQL facets/counts и отдельный bounded maintenance
worker остаются в B229. Source sync намеренно paused до этого worker; текущий
persisted catalog read-only path не следует выдавать за полностью работающий
ingest.
