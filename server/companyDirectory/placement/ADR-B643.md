# ADR B643: компания — источник вакансии, размещения — отдельно

Статус: принято, 12.11.2026. Область: `server/companyDirectory/`, `server/vacancies/`.

## Контекст

Вакансия попадала в пул под `source_id` площадки, а не работодателя. Одна и та же
вакансия приходит с сайта компании, из ATS, из канала LinkedIn и от агрегатора
(hh, getmatch, habr). Карточка получала ссылку по приоритету источника, а не по
тому, где вакансию реально надо открывать. У агрегаторных вакансий не было
связи с компанией, у компаний без сайта и ATS — очереди на поиск доски.

## Решение

Компания — источник вакансии. Размещения (сайт → ATS → LinkedIn → агрегатор)
хранятся отдельно, в боковых таблицах (`placement/placementSchema.ts`,
только `CREATE TABLE/INDEX IF NOT EXISTS`, без ALTER и backfill в окне выкатки):

- `company_placement` — размещение компании: тип, провайдер, slug, приоритет.
- `vacancy_company` — связь вакансии пула с компанией.
- `company_discovery_queue` — компании, найденные агрегатором без сайта и ATS.

Правила:

1. `sourceKind(sourceId)` (`vacancies/poolLiveness.ts`) — единственное место,
   где `source_id` превращается в тип: `ats` (с провайдером), `employer_site`,
   `aggregator`, `hh`, `linkedin`. `placementTypeOf` сводит их к четырём типам
   размещения. Приоритет (`placementModel.ts`): сайт 1, ATS 2, LinkedIn 3,
   агрегатор 4; меньше — лучше.
2. `pickPrimaryUrl` (`vacancies/vacancyDeduplicator.ts`) меняет только
   `primaryUrl` кластера: среди источников высшего приоритета берётся лучший
   по рангу размещения. Название, компания и адрес карточки не сдвигаются.
3. Связь агрегатора с компанией (`aggregatorLinkage.ts`) — только точная:
   `exact_name`, `exact_name_single_word` (однословное имя — отдельный,
   более осторожный режим), `hh_employer_id`. Нечёткого сопоставления нет.
4. Сайт компании ищет детерминированный резолвер без модели
   (`siteDiscovery/deterministicResolver.ts`): ссылки работодателя на hh,
   сигналы страницы карьеры, подбор по доскам ATS; лимит на хост
   (`hostLimiter.ts`), честные статусы, kill switch.
5. Страницы с JS-отрисовкой читает отдельный render worker, вне event loop
   HTTP-процесса.
6. `careersPrune.ts` снимает с обхода сайты, где страница карьеры исчезла или
   не даёт вакансий; снятие обратимо.
7. Охват виден админу через coverage API
   (`placementCoverage/coverageReport.ts`): сколько компаний с сайтом, ATS,
   только агрегатором, сколько в очереди.

## Отклонённые варианты

- **Поиск сайта и ATS моделью.** Недетерминированно, платно на 60К названий,
  результат не проверить без человека; выдуманные адреса хуже пустых.
- **Колонки в `vacancy_pool_index` (ALTER).** Прод-БД 3,8 ГБ, окно здоровья
  20 с; боковые таблицы безопаснее и откатываются удалением.
- **Слияние кластеров по `company_key` (B643-12) — отклонено CPO 12.11.**
  Пробный прогон: 3 095 новых слияний; в выборке из 100 пар верны 2.
  Сопоставление компании верно в 100 из 100, ошибка целиком в правиле
  дедупликации, у которого нет проверки локации. Причины ошибок:
  - одно название в разных городах (Fresenius, Heidelberg) — 65 пар;
  - слабый порог названий: «Менеджер по обслуживанию» и «Менеджер по продажам»
    при пересечении 0,5 (МТС) — 30 пар, все со связью по однословному имени;
  - разные роли или страны — 3 пары.

  Вернуться к слиянию можно только с проверкой города или удалёнки, более
  строгим порогом названий и без связей, опирающихся лишь на однословное имя.

## Последствия

- Ссылка карточки ведёт на лучшее размещение работодателя; кластеры не
  меняются, риска для адресов каталога и связей с ролями нет.
- Новые типы источника добавляются в `sourceKind()` и ранг размещения, а не
  проверкой префикса `source_id` по месту.
- Боковые таблицы пишутся фоном; охват растёт по мере прохода, а не сразу.
- Остаток: часть проверок префиксов `source_id` осталась вне `sourceKind()`,
  потому что у них иная семантика (приоритет дедупликации 100 для
  `src-company-li-`, разбор ключа доски в `directoryFromBoards` и
  `placementLinkage`, `aggregatorLinkage` — только каналы компаний LinkedIn).
  Замена изменила бы поведение; сводить нужно отдельной задачей с тестами.
